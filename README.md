# Multiply or Release? — Unity 复刻原型

按你的规格搭的可运行原型。目标平台 macOS Intel，Unity **2023.2.20f1c1**。

---

## 一、怎么跑

1. Unity Hub → Add → 选这个文件夹 `MultiplyOrRelease` → 用 2023.2.20f1c1 打开。
2. 首次打开会编译脚本、生成 `Library/`，大概 1～3 分钟。
3. **随便哪个场景直接按 Play 就能跑**——整个游戏是运行时用代码搭出来的，不依赖任何场景、预制体、材质或美术资源。
4. 要打包：菜单 `Multiply or Release → 创建主场景并加入 Build Settings`。

### 操作
| 键 | 作用 |
|---|---|
| `1` `2` `3` `4` | 切换左栏底部武器栏聚焦的阵营 |
| `K` | 直接打死当前聚焦阵营的炮台（验证「亡语 + 复活」） |
| `B` | 刷一颗 999M 调试大球（引力球但未到中子星） |
| `V` | 刷一颗 **99M 吸血球**（验证螺旋特效 / 吸血碰撞，第 113 轮） |
| `F1` | 开关性能统计面板 |
| `-` / `+` | 模拟速度 ×0.5 / ×2（0.125× ~ 8×） |
| 滚轮 | 缩放右侧战场视图 |
| `WASD` | 平移右侧战场视图 |
| `R` | 复位战场视图 |
| `Tab` | 开关设置面板（阵营数 / 阵营颜色）；手机点右上角「设置」 |
| `空格` | 暂停 / 继续（画面冻结，但设置面板照常能点） |

## 二、本版按你的纠正改了什么

| 你的纠正 | 现在的实现 |
|---|---|
| 乘倍判定框低于显示框 | 乘倍区做成**两层**：上面白色「显示框」写 xN，紧贴下面一条**更宽的灰条**才是真正的判定框（`Cfg.GateTriggerYOffset`），球要碰到下面那条才倍增 |
| 子弹打到 <100M 己方球 → 加血 + 微弱推力 | 己方球 `Value += 4`，推力系数 0.35 |
| 子弹打到 ≥100M 己方球 → 弹开 + 微弱推力 | 子弹**原路反射**继续飞，不消耗；只给 0.35 的推力 |
| 子弹打到敌方球 → 扣数值 | 敌方球/大球 `Value -= 4` |
| 1 发子弹数值 = 4 | `Cfg.BulletDamage = 4` |
| 护盾归零后，敌方大球或子弹打到本体才死 | 护盾 >0 时只磨护盾（判定框是个大圈）；护盾归零后**关掉护盾判定框**，敌方碰到本体判定框才 `Die()` |
| 地图 1024×1024 像素，单像素数值 1 | 战场就是一张 1024×1024 的 Texture2D；每涂一个像素扣 1 点数值（`Cfg.PixelCaptureCost = 1`） |
| 亡语换算 1:1 | 增倍球 → 大球 1:1；子弹 → 大球 1:1 |
| 复活覆盖 | 子弹/护盾按 `=` 赋值覆盖 |
| 大球数值变成原本的 60% | 复活后大球**保留**在场上，数值变成 60%（不再被吃掉） |
| >1M 大球向后喷子弹提速 | 每 0.25s 往速度反方向喷 1 发 **数值 128** 的子弹，反冲提速；速度快过 7m/s 时不喷 |
| 增倍球文字四舍五入 | 独立格式化函数：33554432 → `34M`，16777216 → `17M`，4096 → `4K` |
| 四家共用一间增倍区 | 确认 |
| 海量粒子 + 百万像素要优化 | 见下面「四、性能」 |

## 二·一、第 7 轮

> **你说得对，问题不在球，在我的地图世界尺寸。**

我把地图世界宽度定成了 96m，但按录像反推应该是 **14m**：
- 录像里 868K 的大球半径 ≈ 地图的 **8.5%** → 0.085 × 地图宽 = 公式给的 1.15m → **地图宽 ≈ 13.5m**
- 同一个 14m 下，1M 护盾的公式半径 0.868m = 地图的 **6.2%**，也正好是录像里护盾圈的比例

所以**两个公式本来就是自洽的**，一个显示倍数都不用加。这一版：

| 项 | 改动 |
|---|---|
| `Cfg.MapWorldSize` | 96 → **14** |
| `ShieldVisualScale` / `BigBallVisualScale` | **全部去掉**（=1），直接按公式 |
| 地图相关的距离 | 全部按新尺度重算（出生地半径 11→1.8、近防 16→4、引力范围 60→8、子弹速度 22→7、拖尾长 3.6→0.55 …） |
| **`CornerOf` 写死了 0.25/0.75** | 这是「炮台怎么改都没往里移」的真正原因 —— 现在读 `Cfg.HomeCornerFraction`（0.32） |
| **乘倍框被我上一轮拉长，把中间通道堵死了** | 改回**对着帧量**的 1.47 / 0.80 / 1.12 / 0.80 / 1.47 |
| **x16 只画了个白框，黑字在黑背景上看不见** | 改成：**灰色楔形本体** + 压在上面一块**白底标签牌**，黑字写 "x16" —— 和录像一致，也看得见了 |
| **武器区太宽** | 只收窄武器区（`WeaponZoneWidth = 区宽 − 墙厚×2 − 0.3`），**没有动墙、没有动乘倍区** |
| **固定阻挡球位置** | 改成**两排**：紧贴乘倍区下方一排密的（21 颗，y=−2.25），再往下一排疏的（11 颗，y=−5.5）；武器框上沿那几颗贴到武器栏上边缘 |
| **乘倍后要立刻传送回发射炮台** | 现在撞到门 → 数值乘倍 → **立刻传回炮口**并重新给初速度方向（发射炮台同时做一下后坐） |
| **子弹涂色要扣数值** | 和大球同一条规则：**1 像素扣 4 点**；数值 ≤ 0 直接删除自己 |
| **炮台死亡要有爆炸动画** | 每个增倍球变亡语大球时，原地放一个**扩散圆环 + 收缩光球**的爆炸特效 |
| **炮台大小恒定、且做大了** | `TurretRadius = 0.62`（14m 地图上 4.4%），**不再随护盾量变化**；子弹/护盾文字字号也由它算出，所以同样是恒定的 |
| **子弹文字离炮台太远** | 改成**紧贴炮台**上方（不是贴护盾圈） |

## 二·四、第 4 轮：**结构性错误改正**（重看录像后）

上一版我把整个结构搞错了，这一版按录像重做。

| 我搞错的 | 真相（录像里看得很清楚） | 现状 |
|---|---|---|
| **左栏那个写着 x16 的灰色楔形是炮台** | 它是**乘法门**（x16 是倍率，下面那个 `0` 是它的**计数器**） | 改成 `MultiplierGate.CreateX16`，倍率写在门身上、计数器画在它下面 |
| 四个炮台在增倍区里 | **四个炮台和护盾在右栏战场的四角** | 炮台搬到战场，`Turret.Create(faction, battleRoot)` |
| 左栏少了东西 | 左栏从上到下是：**x16 门** → 增倍球 → **x2 x8 x4 x8 x2 两组门** → **一排等距的固定阻挡球** → **中间向上飘的缓冲球云** → 7 格武器栏 | 全部补齐，`PegRowCount = 11` 那排固定阻挡球（两端两颗更大）也在 |
| 称号 / 名称系统 | 你先不要了 | **整个去掉**，炮台只显示「上方子弹数、下方护盾量」 |
| 子弹 / 增倍球的形状 | 子弹是**阵营色小圆点**，拖尾是**白色条纹**；增倍球的拖尾是**三角形的**（圆头 + 长三角尾） | 子弹 = 圆点 + 白色条纹拖尾；增倍球 / 大球 = 圆头 + 三角尾的彗星 |

### 顺带查出来的两个真 bug

1. **拖尾缩放多乘了 4 倍**。`SetStreakScale` 内部又乘了一次 4，而调用方已经把粗细乘过 2 —— 结果拖尾比球还粗，看起来就是个三角形。现在换成 `SetComet(t, rootScale, 头直径, 尾长)` / `SetStreak(t, rootScale, 长, 粗)`，参数全是世界单位，不会再算错。
2. **两个 Kinematic 刚体之间 Unity 不派发触发事件**。子弹原来是 Kinematic，炮台护盾判定框也是 Kinematic → 「敌方子弹打到护盾」永远不会触发。子弹改成 Dynamic（无重力、无阻尼、不睡眠）就正常了。

### 一个我拿不准、需要你给数的

`Cfg.ShieldVisualScale = 10`。
公式 `ln(1M)/18+0.1 ≈ 0.868m` 直接投到 96m 宽的地图上只有 0.9%，
而录像里护盾圈占了地图宽度的 **12%** 左右，所以我乘了 10 把它放大到接近录像的比例。
**这个数是我对着录像估的**，你给准确值（或者告诉我"护盾半径就是公式值、地图没那么大"）我替换掉。

## 三、已按规格实现的规则

**开局**：四家各涂一圈自身周围领土 · `100000` 子弹 + `1M` 护盾 · 每阵营 2 个增倍球 · 每 60 秒 +1 个增倍球

**半径公式**（原样实现，`math.log` 按自然对数）
- 护盾：`radius += ((ln(护盾值)/18 + 0.1) - radius) / 5.0`
- 大球：`radius += ((ln(大球值)/8.3 - 0.5) - radius) / 4.0`
- 增倍球：`radius = ln(增倍球值)/55 + 0.05`

**大球碰撞**（★ 第 92 轮：三条的比例统一改成 **3/4**）
- 不同阵营：**双方各扣 `min(a,b) × 3/4`**
- 同阵营双方都 `< 100M`：只给物理推力
- 同阵营有球 `> 100M`：该球产生引力（只吸引同阵营），小球撞上去把 **自身的 3/4** 数值转给它
- 两颗引力球相撞：小的把 **自身的 3/4** 转给大的

**亡语**：炮台死亡 → **每个增倍球各自变成一颗独立大球** + **子弹单独算成一颗大球**（不合并）

**复活**（死亡 60 秒后大球回到出生点）
```
增倍球数量 += toInt(ln(大球数值) - 4)
子弹       = 大球数值 * 0.1
护盾       = 大球数值 * 0.05
大球数值   = 大球数值 * 0.6      ← 大球留在场上，不是被吃掉
```

**显示**
- 子弹数量：三位分级 + 空格 + 居中 → `2 531 742`
- 护盾 / 大球：`K M B T P E` 后缀、**逗号做小数点** → `1,0M`、`269M`、`8,4M`
- 增倍球：同后缀但**四舍五入到整数** → `34M`、`17M`、`4K`
- 黑白文字由阵营色亮度决定（阈值 0.33）：黄/绿/红用黑，蓝用白

## 四、性能（你要求「海量粒子 + 百万像素」）

已经做的：

1. **地图 = 一张 Texture2D**。1024×1024 = 1,048,576 像素，只用 **1 个 DrawCall**；染色只改 texel，不产生任何 GameObject。
2. **按块跟踪脏区**。整张图切成 64×64 的块（16×16 = 256 块），染色时只标脏覆盖到的块，每帧只把脏块推给 GPU。四家分散在地图四角时，这避免了「包围盒横跨全图 → 每帧白推 4MB」。脏块超过 1/4 张图时自动退化成整张推一次。
3. **只在真正涂到东西时才上传**。没人在刷地的时候，地图这一帧零开销。
4. **子弹对象池**。子弹只创建一次，之后 `SetActive` 反复复用，不用 Instantiate/Destroy；场上上限 `Cfg.MaxLiveBullets = 6000`，超了就不再生成（宁可少画也不掉帧）。
5. **生命周期集中驱动**。所有子弹在 **BulletPool 的一个 Update** 里统一 tick，而不是几千个 MonoBehaviour 各自 Update。
6. **回收用交换删除**，避免 `List.RemoveAt` 在长列表上的 O(n²)。
7. **上传缓冲区复用**，热路径里不分配内存。
8. **HUD 可关**（`F1`）。`OnGUI` 在几十个标签时没问题，但如果你要压帧率可以关掉。
9. **统计面板**：FPS、当前子弹数 / 池大小 / 因为超上限被拒的次数、每帧上传的像素数 —— 你可以直接看到瓶颈在哪。

如果帧率还不够，下一步可以按这个顺序动：
- 把地图降成 `R8`（只存阵营索引）+ 一个 lookup 上色，像素内存从 4MB 降到 1MB；
- 把大球/增倍球也换成「一个 Mesh 一次画完」而不是每个球一个 SpriteRenderer；
- 地图上传改成每 2 帧一次（视觉上几乎看不出来）。

# 第 10 轮：射速理解错误 + 子弹携带数值

## 我把「1024/tick」理解错了两件事
1. **不是「每帧 1024 发」** —— 那个把子弹池顶满 12000，直接卡死。
2. 正确的意思是**每一发子弹携带的数值**。

## 你给的正式公式（已实现）
```
单发子弹携带数值 = 总子弹数 / 512.0 + 1
```
- `Cfg.BulletValueFor(总子弹数)`，`Turret` 每次开火都现算
  （所以同一家不同时刻打出的子弹，携带数值不一样）
- 开局 10 万子弹 → 单发 **196.3**
- **涂地规则不变**：1 像素扣 4 点数值 → 一发子弹能涂 ≈ 单发数值/4 个像素
- `Bullet._paintBudget` 直接等于这颗子弹携带的数值（原来写死 4，等于一发只能涂 1 个像素）

## 拖尾长度跟着数值走
```
Cfg.TrailLengthFor(数值)  →  ln(1+数值)/ln(1025) × 0.45m，夹在 [0.06, 0.60] 之间
```
数值 196 → **0.34m**；数值 1024 → 0.45m；再大也只到 **0.60m 封顶**（你说过「无论如何不会像现在这么长」，上一版是 0.70m）。

## 射速
`Cfg.BulletsPerTick = 1`（每物理帧 1 发 = **120 发/秒/炮台**，原来是 9/秒×6 发 = 54/秒）。
等你给完整的射速规则再改。

## ① 墙跑到乘倍区里了

`x2/x4/x8` 旁边那些灰色长框，规格说它们**和下面的灰球一样有阻挡作用**。
之前只画了图没加碰撞体 —— 现在每根立柱都挂了 `BoxCollider2D` + 墙材质。

## ④ 乘倍了为什么数值还会变小
`MultiplierBall.FixedUpdate` 里我写的是 `Value *= 0.9995` —— 那是**在扣数值**，
所以乘倍之后数值反而慢慢往下掉。你的原话是「逐渐缩小自己的**体积**」。
已改成：数值**只增不减**；另有一个独立的**体积倍率** `_sizeMul` 每 tick ×0.9995 作用在**显示半径**上，
乘倍 / 选武器 / 重新投放时归 1。

## ⑤ 子弹撞墙要反弹
以前 `Bullet.Tick` 里是「飞出 x<-260 / x>300 … 就回收」，等于子弹直接飞出地图。
现在每帧检查地图边界 `[0, MapWorldSize]²`，越界就夹回去并 `Reflect()`，反弹次数用 `BulletMaxBounces` 兜底。

## ⑥ 射速公式更新
```
单发子弹数值 = 总子弹数 / 64.0 + 1        （原来是 /512）
```
开局 10 万 → 单发 **1563.5**。

## ① 涂地：1 像素 = 1 点
`Cfg.PixelCaptureCost = 4.0 → 1.0`。装满整张 1024² 需要 **1,048,576** 数值（SmokeTest 里有断言）。

## ② 增倍球「拖尾半径和本体对不上，显得球很大」——找到真因了
**`TrailRenderer` 的宽度是「世界单位」，不受 transform 缩放影响。**
我写的 `startWidth = 1.0f` 意味着拖尾有 **1 米宽**，而球本体只有 `2×半径`（比如 0.47 米）——
所以整颗球看着就是个大气球，尾巴比本体宽一倍多。
现在每帧在 `RefreshRadius()` 里按半径重设：`startWidth = 半径 × 2`，和本体一模一样。

## ③ 浮力区「依然无效」——两个原因叠在一起
1. **有效范围太矮**：只按图上那一排箭头（1.5m 高）施力，球是「一掠而过」，
   凭肉眼根本看不出被托起来过。现在**有效**范围一直向上延伸到第二排小阻挡球，
   形成一条通道（箭头本身还是照图画在原来那一排）。
2. **小球太沉**：质量下限 `BallMassMin = 0.35` → 数值 1 的球重 3.43N，浮力 4.35N，
   净上升力只有 0.92N，几乎推不动。现在下限降到 **0.10**：

```
浮力        4.35 N
数值1 球重   0.98 N  → 明显往上飘
262K  球重   4.35 N  → 恰好悬停
1M    球重   4.73 N  → 压得下去
```

战场边界墙 `1.5m → 0.30m`（1.5m 在 14m 的地图上占 10.7%，确实是一圈厚边框）。

`总子弹数 / 64 → 总子弹数 / 1024 + 1`。开局 10 万 → 单发 **98.7**。

## 性能：子弹渲染整个换了（这是齐射卡顿的主因）

## 代价怎么降下来的
以前一颗子弹 = 刚体 + 碰撞体 + 一个 TrailRenderer。子弹一多，**物理引擎和渲染两端一起炸**。
现在：

| | 以前 | 现在 |
|---|---|---|
| 位置更新 | Rigidbody2D 积分 | **自己 `Pos += Vel * dt`** |
| 和地图边界 | 手写夹取 + 反射 | 一样（本来就没用物理） |

物理世界里现在只剩：4 个炮台、若干大球、增倍区的球和钉子 —— 几十个刚体，怎么都不会卡。

# 修复：子弹不涂领土了（去物理化的那一版引入的回归）

用户报：「卡是不卡了。子弹涂领土的功能失效了。」——**完全对得上代码**。

## 根因：`Step` 用返回值报死，池却把返回值扔了
`Bullet.Step()` 回 `false` 表示「这颗该回收了」，但它**只有**在护盾/大球那几条路径上才自己 `Release()`；
「数值耗尽」「寿命到」这两种是**靠返回值**通知外面的。

而去物理化重写时，池的循环写成了：

```csharp
b.Step(dt, ((i + phase) % stride) == 0);   // 返回值没人接
```

后面的清理只认 `b.InUse` —— 于是**打空的子弹永远赖在 `_active` 里**：

1. `_active` 只涨不跌，几分钟就上万；
2. `stride = _active.Count / MaxPaintOpsPerFrame` 跟着水涨船高；
3. `allowPaint = ((i + phase) % stride) == 0` 几乎恒为 false；
4. **子弹照样在飞、帧率照样好看，但再也没有一颗轮得到刷地。**

修法就一行 —— 把返回值吃掉：

```csharp
if (!b.Step(dt, ((i + phase) % stride) == 0)) b.Release();
```

## 顺带堵掉同一个症状的第二条路
轮转预算 `stride` 是按**全部**子弹数摊的，可飞在**自家领土**上的子弹本来就刷不出东西
（`Paint` 里 `have == want` 直接跳过），却照样占一个名额。某家领土一做大，
大部分子弹都在自家地上飞，真正该刷地的那几颗就被稀释到几乎轮不上 —— 症状一模一样。

所以加 `Battlefield.OwnedBy(world, factionIndex)`（O(1) 查表），
子弹在自家地上直接跳过刷地判定。中立地（`0`）不算自家，照样会涂。

# 第 30 轮：拖尾换回 Unity 自带 + 文字块上移 + 跳帧定位

## ① 子弹拖尾 → Unity 自带 `TrailRenderer`（保留「没有子弹上限」）
上一轮为了让子弹上万，我把拖尾塞进了那个合批 Mesh（一段直锥形）。
现在按规格换回自带的：`Bullet.CreateBlank` 里给每颗子弹挂一个子物体 `Trail`，
加 `TrailRenderer`。它按**时间**采样，天然就是「长度 = 速度 × 时间，快时该长就长」。

「没有上限」这条不能丢，所以拖尾这边做了这些事：

| 做法 | 为什么 |
|---|---|
| 材质**全局共享一份**（`Bullet._trailMat`） | 每颗一份 Material = 每颗一次 SetPass，这才是 TrailRenderer 贵在哪 |
| `time = 0.22s`、`minVertexDistance = 0.03` | 点数少且够顺滑（必须**小于**子弹一物理帧走的 0.037m，否则整条拖尾只有几个折点） |
| `numCapVertices / numCornerVertices = 0` | 圆头/折角顶点全关，顶点数最小 |
| 闲置子弹整只 `SetActive(false)` | 池里的子弹**零开销**，只有活着的那几千颗在画 |
| `autodestruct = false` + `Clear()` | 对象池复用：不清的话新的一条会从上一世的终点连过来 |
| `BulletRenderer` 里只剩圆点（每颗 4 顶点、1 个 submesh） | 拖尾搬走了，网格少一半顶点 |

图层：**拖尾 `sortingOrder = 1`**（规格「墙要在子弹拖尾上面」—— 边界墙是 2），
圆点仍是 40（在墙之上、大球 60 之下）。

## ② 名称三行 + 护盾：整体往上拉
`DrawTurretPlate` 里原来从 `y + corePx + 2` 开始往下排。
新增 `Cfg.TurretLowerBlockLiftFactor = 0.45f`，改成
`y + corePx × (1 − 0.45) + 2` —— 单位是**炮台屏幕半径的比例**，
不写死像素（第 6 条教训：写死像素换个分辨率就错位）。死亡倒计时那行用同一个基准。

## ③ 跳帧：先定位，再动手
「偶尔跳帧」这种事不测就是在猜，所以：

**A. 修掉两个确定会抖的地方**
- **子弹位置做物理步之间的插值**：物理 60Hz、渲染 60Hz 但**两者不同相**，
  不插值的话子弹就是「走一步、停一下」——本来就长得像跳帧。
  做法：`Bullet.PrevPos` + `BulletPool.LateUpdate` 里算 `alpha = (Time.time − Time.fixedTime)/fixedDeltaTime`，
  **每帧**把 transform 挪到插值位置（拖尾跟随 transform 采样，所以也必须是每帧），
  圆点用同一个插值点画 —— 圆点 / transform / 拖尾三者不会错开。
- **子弹池批量扩容**：`Rent` 以前是「池空了就 new 一个」，一颗子弹要建 2 个 GameObject + 一个
  TrailRenderer，齐射那一瞬间就是几十次单颗分配抖动。现在一次建 `BulletPoolGrowBatch = 128`，
  预热也从 2560 提到 4096。

**B. 加一条能量出「哪一段在跳」的 F1 读数**
新增 `Assets/Scripts/Core/Prof.cs`（每段只取两次 `Stopwatch` 时间戳，开销可忽略），
F1 面板多一行：

```
frame ms  avg 16.7  max 41.2   |   pool 0.8  flush 2.1  hud 1.3
```

`max` 是**最近 120 帧的最大值** —— 用平均值会把尖峰糊掉，正是它才看得见跳帧。
`pool` = 子弹池的物理帧（积分 + 网格 + 碰撞）、`flush` = 地图贴图上传、`hud` = OnGUI。
**哪一列跟着尖峰一起跳，就是它**，不用再猜。

**C. 顺手省掉的每帧开销**
`FitFontSizeExact` 要在 128px 基准字号下跑一次 `CalcSize`（一整轮文字排版），
每帧对每个文字各来一次，二十来次就是白白的一两毫秒。新增测量缓存
`MeasureAtBase`（只缓存**测量**结果，按目标宽度换算是纯算术；按 `GUIStyle` + 文字分桶，
子弹数每帧都在变所以桶满了就清）。

## 回归测试
`SmokeTest` 加了 6 条：拖尾确实是 `TrailRenderer` / 发射中在记录 / 有长度和宽度 /
用共享材质 / **图层在圆点之下**（= 在墙之下）/ 回收后停止记录。共 91 条，`ALL PASS`。

# 第 32 轮：引力略微调大 + 拖尾半径永远大于子弹半径

## ① 引力略微调大
`GravityOnBullet 12 → 15`（+25%，「略微」）。这条是**引力球对所有阵营子弹**的吸引力，
也就是「子弹飞过引力球时被拽弯」的那个力；范围 `GravityMaxRange` 没动。
（`GravityOnBigBall = 0.05` 那个「对大球的微小作用」没动 —— 你说的应该不是它。）

历史：26 → 7 →（你说「略微调小」）4 → 你又说「引力不见了」→ 12 → 现在 15。

## ② 拖尾半径永远大于子弹半径
之前 `BulletTrailThickness = 0.058f` 是**写死**的：
拖尾半径 0.029，而子弹半径 0.032 —— **拖尾比子弹还细**，看着就是一根线穿在珠子中间。

修法不是把 0.058 改大一点，而是**让宽度从子弹自己的半径推出来**，这样以后再改子弹半径、
或者齐射弹丸用了别的半径，都不会又翻车：

```csharp
public const float BulletTrailRadiusFactor    = 1.40f;   // 头：拖尾半径 = 子弹半径 × 1.40
public const float BulletTrailEndRadiusFactor = 1.05f;   // 尾：拖尾半径 = 子弹半径 × 1.05
```

```csharp
// Bullet.Launch —— 每颗子弹按**自己**的 _visRadius 设宽度
_trail.startWidth = _visRadius * 2f * Cfg.BulletTrailRadiusFactor;
_trail.endWidth   = _visRadius * 2f * Cfg.BulletTrailEndRadiusFactor;
```

两个系数都 **> 1**，所以整条拖尾（不只是头部）都比子弹粗，还留了一点收窄的锥形。
`BulletTrailThickness` / `BulletTrailEndWidthFactor` 两个写死的常量删掉了。

## 回归测试
新增 3 条，而且是**拿实数比**的：

```

[SMOKE] OK   拖尾比子弹粗（尾） 拖尾半径 0.034
[SMOKE] OK   齐射弹丸的拖尾也比它自己粗 拖尾半径 0.045 > 弹丸半径 0.032
```

第三条特意换成**另一个半径**（齐射弹丸，`heavy=true`）再验一遍 —— 它防的正是

# 第 33 轮：涂色一卡一卡 + 大球盖不住文字 + 护盾圈比判定小

## ① 涂色「卡一下然后一下在涂」—— 地图贴图每 6 帧才推一次
你说的「**无论大球还是子弹**，涂色都是一卡一卡的，卡一下然后一下在涂，循环往复。
本身掉帧其实还好」——**「掉帧还好」这句就是线索**：卡的不是帧率，是**领土的更新节奏**。

真因：`Cfg.MapFlushIntervalFrames = 6`。像素**每个物理帧都在写**（写进 native 缓冲，不花什么钱），
但 `Texture2D.Apply()` 每 6 帧才做一次 —— 于是画面上的领土是 **10Hz** 一帧一帧地长出来的。
帧率是 60，所以「帧率还好」，但领土自己在跳。

（上一轮我刚把子弹改成**插值渲染**、变得很顺，对比之下就更容易看出来。）

改成 **每帧都推**（`MapFlushIntervalFrames = 1`）。4MB 上传，现代机器 <1ms ——
F1 那行 `flush` 就是它的实测耗时，真嫌贵就调回 2。

## ② 大球从炮台文字上经过：要**大球盖住文字**
HUD 文字全部走 `OnGUI`，而 **IMGUI 永远画在所有相机之上** —— 所以无论大球 sprite 的
`sortingOrder` 调到多高（现在是 60/61），文字都还是压在它上面。

做法是**反过来**：把大球在 IMGUI 里**再画一遍**，插在炮台文字之上、大球自己的数值之下
（`HudOverlay.DrawBigBallOverlay`，黑描边 + 阵营色本体，尺寸/位置和 `BigBall.ApplyRadius` 一致）。
于是自下而上是：

```
炮台文字（子弹数 / 名称三行 / 护盾） → 大球本体 → 大球自己的数值
```

## ③ 子弹拖尾被护盾挡住 + 护盾纹理半径小于实际半径

**(a) 拖尾图层**：上一轮我为了满足「墙要在拖尾上面」，把拖尾压到 1（墙是 2）——

| **边界墙** | **15**（原来是硬编码的 2） |
| 子弹圆点 | 40 |

这几个值现在集中在 `Cfg` 里（`ShieldFillSortingOrder` / `ShieldRingSortingOrder` /
`BulletTrailSortingOrder` / `BattleWallSortingOrder` / `BulletDotSortingOrder`），
测试直接拿它们两两比较，不再各写各的。

# 第 34 轮：引力球特效 / 护盾击碎动画 / 散弹解封 / 护盾羽化

## ① 引力球的**持续**特效（`Sim/GravityFx.cs`）
规格要的是「持续」，所以做成**一圈一圈往外扩、边扩边淡的涟漪**，而不是一次性爆闪 ——
一次性闪完就安静了，又和普通大球长得一样。

实现：`Cfg.GravityFxRingCount = 3` 个软边环（`Primitives.SoftRing`），
相位错开 1/3，各自按 `Time.time / GravityFxPeriod` 循环缩放（1.0 → 2.1 倍球半径）+ 平方淡出。
挂在大球**下面**当子物体（大球的缩放/移动它自动跟），图层 `GravityFxSortingOrder = 57`
在大球本体（60/61）之下，所以只看得见冒出球外的那一段。
`BigBall.FixedUpdate` 里按 `IsGravityBall` 开关（只有状态变了才动 `SetActive`）。

## ② 护盾被击碎：半径 0.8 秒缩到 0
之前的真因是 `_shieldFill.enabled = hasShield` —— 护盾值一归零，**画面啪一下就没了**，
根本来不及看（`ShieldRadius` 自己那点缓动也一起被抹掉了）。

现在 `Turret` 里有个小状态机：护盾从 >0 变 0 时记下**碎之前那一刻的半径**，
在 `Cfg.ShieldBreakTime = 0.8s` 内把**显示半径**按比例缩到 0，缩完才隐藏；
护盾回来（复活 / 加盾）就立刻取消动画。
判定不受影响 —— `_shieldTrigger` 和碰撞那套在护盾归零时**立刻**关掉，动画纯粹是显示。

## ③ 发射密集度 ×4 + **散弹解封**
- `BulletFireRate 200 → 800`（发/秒/炮台）。
- ★ 注意：`/1024 → /4096` 这条**其实已经是 4096 了**（第 8 轮就按你说的改过），
  所以这次真正生效的是密集度。于是**每秒泼出去的数值总量变成 4 倍** ——
  如果你要的是「总输出不变、只是更密」，那把 `BulletValueDivisor` 再乘以 4 就行，说一声。

**散弹解封**（`Cfg.BulletValueFor(total, elapsed)`）：

```csharp
public const double ShotValueUnlockTime = 300.0;   // 5 分钟
public const double ShotValueCap        = 4096.0;

double v = total / 4096 + 1;
if (elapsed < 300s && v > 4096) v = 4096;          // 未解封 → 封顶
```

炮台发射和扣弹药**都**走这个带时间的重载（两处必须一致，否则「打出去的」和
「扣掉的」对不上）。对局时间 = `GameWorld.MatchElapsed`。

## ④ 护盾羽化：纹理和判定**共用同一个带宽**
你说的「护盾纹理下面套了个真护盾」——是的：纹理是 `ShieldDisc` 的 alpha 渐变，
底下真正的判定是 `BulletPool.ResolveTurrets` 里那个**硬圆**。现在两者绑在一起：

- `Cfg.ShieldFeatherBand = 0.22`（**一个**常量，两边都用）；
- **纹理**：内侧 78% 实心，最外 22% 渐隐到 0；
- **判定**（`Bullet.FeatherFactor`）：最外那 22% 里**按比例**吃子弹 ——
  最外沿系数是 0（擦着边飞过去等于没碰到），越往里越高，内圈 78% 依旧是 1（和以前完全一样）。
  被吃掉的只是「有效数值」那么多，**剩下的自己带着继续飞**（硬边版本是碰到就全没）。

`BulletPool` 传进去的是「子弹边缘探进护盾多深」（扣掉子弹自身半径），
所以刚好擦到最外沿时系数为 0。

# 第 35 轮：子弹按渲染帧推进（「发几发、停一下」的真因）+ /16384 + 开局护盾

## ① 「发射 4 发、停顿极短、再发 4 发」——子弹在**物理帧**上，画面在**渲染帧**上
你这句话指向的不是射速，是**节拍**。

原来子弹在 `BulletPool.FixedUpdate` 里推进（固定 60Hz），而画面是渲染帧率。
两者只要不是严格倍频，就会出现「这一帧跑了 1 次物理、下一帧跑了 0 次」：

- 0 次的那一帧，子弹位置**根本没动**（上一轮加的插值到 alpha=1 也只能停在原地）→ **看着就是停顿一下**；
- 同一帧里炮台也发不出子弹（`FixedUpdate` 没跑）→ 于是「发几发、停一下、再发几发」。

**改法：子弹按渲染帧推进。** 子弹早就不是物理体了（位置自己积分、碰撞走自建网格、
不用 `Rigidbody2D`），所以搬到 `BulletPool.Update` 是零副作用的 —— 反过来还省掉了插值那套
（`Cfg.BulletInterpolate` 现在关掉了）。给 `dt` 加了上限 `BulletMaxStepTime = 0.05s`，
卡一下的时候别让子弹瞬移穿墙。

## ② 开火也搬到渲染帧，并用**小数累加器**
`Turret.FixedUpdate` → `Turret.StepFiring(dt)`，在 `Turret.Update` 里调。两个理由：

1. 发射和子弹推进必须同一个节拍（不然还是会出现「这帧没发」）；
2. 用累加器而不是 `round(射速 × dt)` —— round 会让每帧的发数在 13 / 14 之间跳，
   累加器是「攒够一发就发一发」，**每一帧都真的在发**，长期平均还正好等于射速。

另外同一帧的这一批**沿炮管铺开**（`SpawnBullet` 的 `ahead` 参数）：
不铺开的话它们会精确重叠成一个小点，看上去「一帧只发了一发」。

## ③ 单发数值 /4096 → /16384
`Cfg.BulletValueDivisor = 16384`。开局 10 万子弹 → 单发 **7.1**（原来是 25.4）。

## ④ 开局护盾 = 8388608
`Cfg.StartShield = 8388608`（= 2^23）。护盾圈半径从 1.13m 涨到 1.28m。

## 回归测试
子弹的回归测试也跟着改了：`Invoke(bp, "FixedUpdate")` → `Invoke(bp, "Update")`，
并且**每一轮手动把子弹挪到一块新地方** —— 编辑器里 `Time.deltaTime` 接近 0，
不动的子弹刷不出新像素就永远死不了，那样测的就不是「数值耗尽 → 回收」了。共 118 条，`ALL PASS`。

# 第 37 轮：涂色断断续续 + 地图填满的账对不上

两个问题其实是**同一条链上的两处**，都跟「谁在刷地、谁付钱」有关。

## ① 涂色断断续续 —— 刷地轮转（`stride`）删掉了
`BulletPool.Update` 里原来有个「每帧只让 `n / MaxPaintOpsPerFrame` 分之一的子弹刷地」的轮转：

```csharp
int stride = Mathf.Max(1, n / 1200);          // 上万颗子弹时 stride 能到 5~8
b.Step(dt, ((i + phase) % stride) == 0);      // 只有轮到的那些才刷地
```

于是画出来的领土是**一串断断续续的斑点**（用户原话：「不是连贯的，断断续续看着很难受」）。

# 第 39 轮：修「刚运行起来就卡崩」—— 是我上一轮引入的死循环

**这是我自己造的 bug**，而且就是你运行的那一刻卡死的直接原因。

## 真因：网格链表用 0 当「空」，而 0 是个合法下标
`BulletPool` 的均匀网格用链表串同一格里的子弹：

```csharp
for (int i = _head[c]; i >= 0; i = _next[i])   // -1 = 空
```

但 `InitGrid()` 里是这么建的：

```csharp
_head = new int[GridN * GridN];
_next = new int[1024];
```

`new int[]` 是**全 0** 的 —— 0 不是「空」，而是「第 0 颗子弹」。而 `_next[0]` 也是 0，
于是 `i` 永远是 0：**死循环，刚运行起来就卡崩**。

## 为什么以前不炸、这一轮才炸
这个网格原来只有两处用：`ResolveTurrets` / `ResolveBigBalls` ——
而它们**紧跟在 `RebuildGrid()` 后面**，所以拿到的时候网格一定是建好的。
上一轮我给近防加了个新查询 `TryFindNearestEnemyBullet`，它是在 **`Turret.Update`** 里调的 ——
**组件之间的 `Update` 顺序没有保证**，完全可能跑在 `BulletPool.Update` 之前，
那时网格还一次都没建过 —— 一上手就是那片全 0 ✗

## 修法
```csharp
Fill(_head, -1);
Fill(_next, -1);
```
（`_next` 扩容那条路径也一起填 —— `new int[]` 同样是全 0，坑是一样的。）
另外给「子弹打子弹」的配对检查加了每帧上限 `Cfg.MaxBulletPairChecks = 20000`：
同一格里的子弹扎堆时那里是 O(k²)，刚出膛的整条弹流能挤在少数几格里，顺手也封个顶。

## 验证（这次是真复现了）
把 `Fill(...)` 那两行注掉重跑，**Unity 直接挂住不复返回**（我终于亲眼看到你遇到的卡死长什么样），
日志里留下一条：

```

（然后就死循环挂住了）
```

加回来后 `ALL PASS`。回归测试里还特意做了防挂处理：**只有链表头确实是 -1 时才真去查询**，
否则将来再有人踩这个坑，测试会**干净地报红**而不是把测试套件挂住。

## 回归测试
新增 2 条（共 130 条，`ALL PASS`）：

# 第 40 轮：「一会儿打一会儿不打」—— 开火和子弹位移用了**不同的 dt**

## 从视频里量出来的证据
把 `lkk.mov` 抽帧放大之后，弹流是一条条**带规律缝隙的短柱**：白段 ≈14px、缝 ≈5px。
按画面比例换算，子弹圆点的间距 ≈ **0.12m**，而正常应该是 `2.2m/s ÷ 60 ≈ 0.037m` —— **差了 3 倍多，而且是周期的**。

缝隙/柱长 = 5/14 ≈ 0.36，而 `(dt − 0.05) / dt = 0.36` → **dt ≈ 0.078s，也就是当时帧率约 13 fps**。
数字对上了。

## 真因
两条路径用了**两个不同的 dt**：

| 谁 | 用的 dt |
|---|---|
| `BulletPool.Update` —— 子弹位移、刷地、碰撞 | `Mathf.Min(Time.deltaTime, 0.05)`（夹过，防瞬移穿墙） |
| `Turret.StepFiring` —— 开火 | **`Time.deltaTime`（原始值）** ✗ |

一帧超过 50ms（帧率低于 20）时：

- 开火按**真实** dt 把一帧的那一批沿炮管铺开 `速度 × dt` 那么长；
- 而子弹这一帧只走了 `速度 × 0.05`。

**每帧就空出一段 `速度 × (dt − 0.05)` 的缝** —— 帧率越低缝越大，看着就是「打一串、停一下、再打一串」。
（帧率够高时 `dt < 0.05`，夹不夹都一样，所以以前看不出来。）

## 修法
把「子弹这一帧推进多久」收成**一个函数**，两边都用它：

```csharp
public static float StepDt(float rawDt) { return Mathf.Min(rawDt, Cfg.BulletMaxStepTime); }
```

`BulletPool.Update` 用它，`Turret.Update` 调 `StepFiring(BulletPool.StepDt(dt))` 也用它。
这样不论帧率多少，**同一帧发射的那一批铺开的长度，正好等于这一帧子弹走的距离** —— 弹流天然首尾相接，永远不会有缝。

## 回归测试
新增 2 条（共 132 条，`ALL PASS`）：

```

[SMOKE] OK   卡顿时：dt 被夹到 BulletMaxStepTime（开火也用这一个）
```

## ★ 但真正该修的是帧率
缝的**宽度**正比于帧时间 —— 你那个视频里大约是 13 fps，所以缝才那么明显。
缝现在没了，但 13 fps 本身还在（子弹密度 ×4 + 没有上限 + 每颗子弹一个 `TrailRenderer`）。
F1 那行 `frame ms avg/max | pool flush hud` 就是用来定位这件事的：
**`pool` 高 → 是子弹本身；`pool` 不高但 frame 高 → 更像是几千个 TrailRenderer 的 draw call。**
把那一行发我，我按读数下手。

# 第 41 轮：「一会儿打一会儿不打」的真凶 —— 网格是回收**之前**建的

**用户判断对了：就是近防那一轮引入的。**

## 经过
`BulletPool.Update` 原来的顺序是：

```
推进 → RebuildGrid() → 子弹打子弹 / 炮台 / 大球 碰撞 → 回收死子弹（swap-remove）
```

网格里存的是 `_active` 的**下标**。而回收是 swap-remove：元素往前挪、`Count` 变小 ——
**网格里却还留着回收前的大下标**。

以前一直没事，因为读网格的两处（炮台判定、大球判定）都在池子**内部**、而且都在回收**之前**跑，
所以拿到的一定是"当下"的网格。

第 38 轮我把近防查询塞进了 **`Turret.Update`** —— 它跑在池子的回收**之后**：

```csharp
for (int i = _head[c]; i >= 0; i = _next[i]) { var b = _active[i]; }   // i 越界 → 抛异常
```

一抛异常，`Turret.Update` 剩下的部分**包括 `StepFiring`** 整段被跳过 ——
**那一帧不开火**。四个炮台各自在不同帧踩到 → 看起来就是「一会儿打一会儿不打」，
而且**症状正好从加近防那一轮开始**，和观察完全吻合。

## 修法（两层）
1. **顺序**：改成 `推进 → 回收 → RebuildGrid() → 碰撞`。
   网格从此一定反映回收**之后**的 `_active`，外部（近防）读它才是安全的。
2. **防御**：三处网格遍历都加了 `if (i >= _active.Count) continue;` ——
   万一将来还有别的地方让网格过期，也**不能抛异常**（抛出去就会掐掉整个 `Turret.Update`）。
   第二层单独就能挡住症状：即使网格是脏的，也只是少判几颗，不会中断开火。

## 验证
回归测试：造 20 颗子弹、把一半标记为死、跑一整轮 `Update`，然后
**遍历整张网格，检查每个下标是否 < `_active.Count`**，并真的调一次近防查询看会不会抛异常。

把顺序改回去重跑（只在 /tmp 副本上改）：

```
[SMOKE] FAIL 网格下标全部合法（网格是回收之后重建的）-> 越界 6 个
```

改回来 `ALL PASS`。

## 顺带
上一轮那个 dt 不一致（开火用真实帧时间、子弹用夹过的）**也是真的**，
两处都会在弹流里留缝，所以两个修复都留着 —— 它修的是「缝」，这一轮修的是「整帧不开火」。

# 第 42 轮：大球涂地**两边都扣**（阵营账上 + 球自己的数字）

你上次说「四家账上还剩 40 万、地图却快满了」，我改成了**扣阵营的子弹数**，

# 第 43 轮：「打了 2M 却打出 24M」—— 开火只扣了「一发」的钱 + 解封前上限改 512

## ① 开火扣钱按**实际发出去的条数**
`StepFiring` 一帧发出去的是 `perFrame` 发（800/秒 ÷ 60 ≈ **13 发**），
但扣钱那里写的是 `SpendShot()` —— **每帧只扣一发的钱**。

于是：**打出去的是账上付出的 13 倍**。你说的「掉了 2M、实际打出 24M」，比值正好 12~13 —— 对得上。

```csharp
// 以前：一帧 13 发，只扣 1 发
SpendShot();

// 现在：扣「这一帧真正发出去的那些」
SpendShots(perFrame, value);
```

改成按条数扣之后，**「子弹文字掉的值」和「真正送出去的数值」永远相等**。
测试拿实数比：

```

```

## ② 散弹解封：解封前的上限 4096 → **512**
严格按解封前 / 解封后两种来：

| | 单发数值 |
|---|---|
| **解封前**（对局未到 5 分钟） | `总子弹数 / 16384 + 1`，但**最多 512** |
| **解封后**（超过 5 分钟） | 一律 `/16384`，**不封顶** |

`512 × 16384 = 8,388,608` —— 也就是**阵营攒到 838 万发之前，这条上限根本咬不到**，
解封一到就立刻放开。边界也测了：

```

[SMOKE] OK   解封后一刻（300.1s）立刻不封顶 -> 61036
```

## ★ 要说清楚的一个后果
以前那个「每帧只扣一发」的 bug 松了 13 倍的账，所以现在按真实条数扣之后：

**阵营的子弹数会掉得快大约 13 倍。** 具体地，射速 800/秒、单发 `B/16384`：

```
dB/dt = −800 × B/16384 = −B / 20.5     →  连射约 20 秒就能把一池打空
```

也就是说**你之前调的那些「密度 ×4 / 除数 ×4」的组合，是在替这个 bug 兜底** ——
账修对了之后，这个天平要重新配一次（抬除数、或者抬初始弹药、或者降射速，都在 `Cfg` 里一个数）。

# 第 44 轮：尾流加速削弱（M 级球别一出来就飞）

## 算一下就知道为什么「太快」
尾流的反冲是**每喷一发给一个速度增量**，所以

```

速度上限 BigBallMaxSpeed = 1.2
```

也就是说 M 级球刚生成、尾流一开，**三分之一秒就变成炮弹**。

```csharp
public const float BigBallJetSpeedGain = 0.04f;   // → 0.015f
```

```

```

**没有动 `BigBallJetRate`** —— 那个管的是尾流的**密度**（你之前专门调过），
调它会把画面上的尾流一起改掉，不是这次的诉求。

```csharp
float along = dx * u.x + dy * u.y;      // 顺着

float d2 = along * along + cross * cross / (k * k);
```

这样**不管子弹朝哪儿飞，涂出来的带子都更宽**（而不是只在某个方向上变长）。
扫描范围也跟着横向放宽了，不然会漏掉边缘那一圈。

# 第 56 轮：帧率优化 —— 拖尾合批 + 投影降频

用户反馈：**帧率卡在 15 左右**。这一轮先把最确定的那块成本拿掉。

## ① 元凶候选：每颗子弹一个 `TrailRenderer`
`TrailRenderer` 的语义最标准，但它是**每颗子弹一个 Renderer**，
在 Built-in RP 下就是**一次 draw call**。场上两千颗子弹 = 两千次 draw call，
Intel Mac 的 iGPU 上这就是几十毫秒 —— 正好是 15fps 的量级。

于是加了 `Cfg.BulletTrailUsesTrailRenderer`（**默认 false = 合批网格**）：

| | `true`（TrailRenderer） | `false`（合批网格，默认） |
|---|---|---|
| draw call | **每颗子弹一次** | **全部子弹一次** |
| 每颗子弹的组件 | 一个 TrailRenderer 子物体 | 无 |
| 每帧 Transform 写入 | 每颗一次 | **零次** |
| 池子预热 | 建几千个 TrailRenderer | 只建 GameObject |

`View/BulletTrailRenderer.cs`（新）把**所有**子弹的尾巴拼进一张 Mesh。
几何是自己按「历史点 + 时间戳」算的，语义和 TrailRenderer 一一对应：
- **按时间过期**（存活 `BulletTrailTime`）→ 「长度 = 速度 × 时间」和
  「数值耗尽后尾巴一点点收掉」都照旧成立；
- **头粗尾细**：宽度沿尾巴从 `BulletTrailRadiusFactor` 插到 `BulletTrailEndRadiusFactor`，
  两个都从 `_visRadius` 派生（规矩：拖尾半径永远大于子弹半径）；
- **头白尾淡**：顶点 alpha 走 `BulletTrailHeadAlpha → BulletTrailTailAlpha`；
- 贴图和 TrailRenderer 画法**共用同一张** `Primitives.Streak`；
- 图层仍然是 `Cfg.BulletTrailSortingOrder = 8`（护盾之上、墙之下，两条规格不变）。

两种画法共用同一套常量，所以**换画法不会让视觉规格漂**。

## ② 投影相机降频
`Cfg.WanderCamInterval = 3` —— 那个「游荡投影」等于**把整个战场再画一遍**
（虽然不看子弹层），而它的产物只是左栏一层 **25% 透明**的底纹。
降到 20Hz 肉眼看不出来，省掉的是一整趟场景渲染。

## ③ F1 面板
第二行末尾加了 `trail mesh` / `trail TrailRenderer`，一眼就能看出当前是哪种画法。

- 合批拖尾真的往 Mesh 里写顶点（8 个点 → 16 个顶点）；
- 所有拖尾共用 **1 个** MeshRenderer（= 1 次 draw call）；

# 第 56 轮 · 修：满屏乱线（Mesh 索引格式）

用户截图：**横穿整张地图的白色乱线 + 四个角放射出来的彩色长条**。

## 真因：`Mesh` 默认的 `IndexFormat.UInt16` 只能索引 65535 个顶点

合批拖尾是「**所有**子弹的尾巴拼进一张网格」：

```
3000 颗子弹 × ~13 个折点 × 2 个顶点 ≈ 78000 顶点  >  65535
```

超过之后 Unity **拒绝写入顶点数据**，而三角形索引还指着那些越界的下标 ——
画出来就是**横穿整张地图的乱线**。子弹圆点那张网格同理
（`BulletRenderCapacity` 往上翻一倍就过 65535，这解释了那些**阵营色的长条**）。

修法两处：`BulletTrailRenderer` 和 `BulletRenderer` 的 Mesh 都设
`indexFormat = IndexFormat.UInt32`。

## 顺带两条

- **图层**：两张网格从默认层 0 挪到 `Cfg.BulletLayer`。
  左栏那个「游荡投影」本来就不该看子弹层，之前网格在 0 层，所以左栏背景里也会画出满屏拖尾。
- **尾巴长度硬上限**：`TrimPoints` 里加了一条 —— 离头超过
  `BulletMaxSpeed × BulletTrailTime` 的点直接丢掉。
  子弹最快也就那么快，那么久**走**不了更远（路程 ≥ 直线距离），所以这个上限
  不可能误伤正常尾巴，但「横穿地图的线」从此画不出来。

## 自检
- 合批拖尾网格用 UInt32 索引；
- 子弹圆点网格也用 UInt32 索引。

# 第 59 轮：弹幕的「缝」（一批子弹要摊在整段扫过的弧上）

用户截图：红色/绿色的弹道一条条分开，中间是空的。原话：
「相当于打 5 发停一下再来 5 发……我想要的是**平均**的密度提升，除非子弹走了很远了否则不留缝」。

## 真因不是「一帧多发」，是**一帧一个角度**

炮台是**转着**打的（`TurretSpinSpeed = 20°/s`），而原来同一帧的这一批子弹
**全部用同一个 `AimAngle`**。所以：

- 一帧只画出一条**射线**；
- 相邻两帧的射线相差 `转速 × dt` —— **20°/s、17 帧时每帧 1.18°**；
- 射线是放射状的，所以**越远越开**：飞出 2~3 米时相邻两条已经分开到露缝，再远就是一条条独立的线。

这正好对上用户那句「**除非子弹走了很远了否则不留缝**」—— 他看到的缝就是这个扇形。

（顺带：`ahead = 速度 × dt × t` 那个沿炮管的铺开是对的，相邻两帧的批次在**径向**上是严丝合缝的；
问题只在**角向**。）

## 解法：把这一批摊在「上一帧角度 → 当前角度」这段弧上

炮台在这一帧里本来就是**从上一帧的角度转到当前角度**的。
所以第 i 发的角度取 `LerpAngle(上一帧角度, 当前角度, (i+0.5)/n)`：

- 一帧画出的是 **n 条射线**（原来 1 条）→ 扇形密度直接乘 n，
  缝被推到 **n 倍远**的地方（17 帧时 n≈80、60 帧时 n≈26 —— 都远超地图尺寸了）；
- **发数、速率、数值一个都没动** —— 只是把同一批子弹摊到它们真正扫过的那段弧上，
  也就是用户要的「**平均**的密度提升」。

实现：`Turret.BatchAngle(i, count)`（拎出来是为了能被自检直接验）+ `AimAnglePrev`，
`SpawnBulletAt(angleAbs, ...)` 走绝对角度。

## 自检：`==== ALL PASS ====`（174 条）
`st.AimAnglePrev = -20 → st.AimAngle = 0`，一批 16 发的角度实测从 **-19.4° 摊到 -0.6°**；
换一批 8 发也摊满同一段弧（密度与每帧发数无关）。

# 第 61 轮：撤回密度 + **修「涂地不花钱」这个真 bug**

## ① 撤回

- `Cfg.BulletEmissionBurst` 5 → **1**（回到每次发射 1 发，`BulletFireRate` 也已经是 800）。
  试过 5 的结论：**又卡、观感也没变** —— 因为「打一批、转个角度、再打一批」
  是**每帧转一个角度**造成的，和一批几发**根本无关**。

## ② ★★ 真 bug：格子是「先涂、后扣」，多涂的全是白送的

用户的原话：「1048576 格，一格数值为 8，总共要 **8388608** 才能填满。但你 60 万就涂满了。」

对的，而且原因正是他猜的那个方向。代码原来是：

```
① PaintLine 把这一帧走过的整条线**全部涂完**（几十格）
② 再拿涂出来的格数去扣子弹的数值
③ 数值不够 → 子弹死
```

问题在 ① 和 ② 之间：**格子已经写进地图了**。
一颗只带 10 点数值的子弹，一帧可以涂掉五六十格（几百点数值），差额全是白送的。
（大球的圆盘 `Paint` 是同一个毛病：先涂满几万格的圆盘再扣，扣不动就 `Max(..., 0.0001)` 收尾。）

### 修法：**先算「还买得起几格」，再让地图只涂这么多格**

- `PaintLine` / `Paint` 都加了 `maxNew`：涂满这个数就**立刻停**（`MarkBox` 里逐格递减）；
- 子弹：`afford = (int)(_paintBudget / PixelCaptureCost)`，`afford <= 0` 就直接消失
  （剩下的零头连一格都买不起）；
- 大球：`afford = (int)(Value / PixelCaptureCost)`。

于是 **涂出去的格数 × 8 ≤ 消耗的数值**，账平了：
填满整张图就是 `1024 × 1024 × 8 = 8388608`。

> 备注：每颗子弹的数值不是 8 的整数倍，所以最后会剩一点「买不起一格的零头」被丢掉
> （当前 150000 子弹时单发约 10.2 → 丢 2.2，约 20%）。
> 想更贴近 8388608 就把 `StartBullets` 提高（单发数值越大，零头占比越小）。

# 第 67 轮：左栏投影里的球被拉长 + 没数字

用户：「看左边。你的摄像机投射出来的背景大球没有文字并且被拉长了。」

这两个都是真的，而且各有各的原因。

## ① 被拉长 —— 渲染贴图的长宽比和那块 quad 不一致

投影相机渲到一张 **正方形** 的 RenderTexture（384×384），
但铺在左栏的那块 quad 是 **竖的**（长宽比约 0.56）。于是贴图被硬拉高 ——
投影里的圆球全变成**竖椭圆**。

修法：`ZoneProjection.RebuildTarget(aspect)` —— 贴图按**面板的长宽比**建
（384 宽 × 686 高），相机自己按贴图尺寸算 aspect，两边就一致了。
`FitToZone` 拿到真实面板尺寸时会调它；比例没变就不重建（不是每帧）。
取景框的水平反弹边界也跟着 `_halfW` 走。

## ② 没数字 —— IMGUI 根本不会被相机渲进 RenderTexture

HUD 的文字全是 `OnGUI`，而 `OnGUI` 是**画在屏幕最上层**的，相机**看不到**它，
所以投影贴图里的大球只有一团颜色。

修法：反过来补 —— 用投影相机把大球的战场坐标映射过去，在 IMGUI 里再画一遍：
- `ZoneProjection.TryViewportUV(world, out uv)`：`WorldToViewportPoint` 得到 (0..1)；
- 那块 quad 的屏幕矩形一算，`uv` 就变成左栏里的屏幕位置；
- 字号 = `2 × 大球半径 × 增倍区相机的 pxPerUnit`（投影是 1:1 的，所以就是这个）；
- 文字和投影一样淡（alpha = `WanderCamAlpha`）—— 它是背景的一部分，不该抢戏。

# 第 68 轮：为什么「粒子」便宜、「子弹」贵 + 还能往哪优化

用户问：别人的 Unity 粒子量比我们大得多却稳 60 帧，我们子弹一多就 20 帧，
还能优化什么？是不是 Windows 比 macOS 吃香？

## ① 先把「不可比」说清楚

Unity 自带的 **ParticleSystem 是引擎原生（C++，job/GPU）在跑**，
渲染走实例化 —— **十万粒子几乎不产生托管（C#）开销**。
我们的子弹是**纯 C# 对象**：每颗一个 `GameObject` + `Transform` + 一个 `MonoBehaviour`，
由 `BulletPool.Update` 里一个托管 for 循环逐颗推进。
**同样「一个单位」，我们的成本是它的几十上百倍** —— 这两个数字本来就不该放在一起比。

## ② Windows vs macOS：不是关键

第四次 F1 读数里 `pool 21ms / hud 9.3ms` —— **瓶颈在 CPU 侧的托管代码**，不在 GPU、不在驱动。
所以：
- 同一个 Mac 装 Windows（Boot Camp）**基本不会变快**（硬件没变）；
- 换一台**CPU 更快、带独显**的 Windows 机器会明显变快 —— 但那是**硬件的功劳**，不是系统的；
- Intel Mac 的 CPU 和核显本来就明显弱于一台普通游戏 PC。

## ③ 还能往哪优化（按「收益 / 风险」排）

| # | 做什么 | 大概收益 | 风险 |
|---|---|---|---|
| a | **子弹改成扁平数组（SoA）** —— `Bullet` 不再是散在堆上的 9000 个对象，位置/速度/拖尾点全放池子自己的大数组里 | **最大**。21ms / 9121 颗 = 2.3µs/颗 ≈ 7000 周期，对「积分 + 涂几格」来说高得离谱 —— 典型的**缓存不命中**（9000 个对象 + 每个两颗小数组 = 两万多个散落的堆对象） | 中（池、渲染器、近防都要改） |
| b | 拖尾**降级门槛调低**（`BulletTrailCrowdCount`）：9000 颗时拖尾网格约 14 万顶点、每帧重建 | 中 | 低（但拖尾会变成直线段） |
| c | HUD 每帧 ~20 个字符串（`BigNumber.*`）改成复用缓冲 / 降频刷新 | 小 | 低 |
| d | 4K → 1440p（若 `frame−pool−hud` 那块是填充率） | 中 | 低（掉画质） |

**这一轮先做了免费的 c 的一半**：
`ResolveTurrets` / `ResolveBigBalls` 原来传的是**捕获局部变量的 lambda**
（每帧每座炮台/每颗大球分配一个闭包 + 委托），改成 `CollectNear()` 收下标 + 复用列表 —— **零分配**。

## ④ 要排序，还是得看 F1
`pool` 高 = 子弹逻辑；`flush` 高 = 地图上传；`hud` 高 = IMGUI；
**`frame` 减掉这三项剩下的** = 渲染 + 拖尾/圆点网格装配 + 填充率。
`bullets N` 是场上子弹数。

## ② ★★ 发射模型改成「单位角度一发」（用户给的模型）

以前是**按时间**发：每帧 `射速 × dt` 发，这一批**角度完全相同**、只沿炮管铺开 ——
所以画出来是「一条放射状的小段」，而相邻两帧的角度差 `转速 × dt` ——
**这正是用户一直说的「打一批、转个角度、再打一批」**。

现在**按转角**发：

```
发数/秒 = 炮台转速 ÷ 单位角度
```

- `Cfg.BulletAngleStepDeg = 0.025°`（20°/s ÷ 0.025° = 800 发/秒，和原来同一个量级）；
- 同一批的角度**摊在「这一帧扫过的那段弧」上** —— 每发子弹占一个角度；
- **想要更密就把这个角度调小**（0.01° ≈ 2000 发/秒）—— 这就是用户说的
  「提升密度的方式是提升单位角度，不是每单位角度多发几发」；
- `BulletMaxPerFrame = 64`：近防猛转（420°/s）时一帧能扫 21°，不封顶会瞬间喷八百发；
- `BulletIdleFireRate = 200`：**炮台几乎不转时**（近防锁死目标后炮管是停住的）退回按时间发，
  否则那一帧一发都不发、炮台会「哑掉」。

自检：`发射模型：转速 20°/s ÷ 单位角度 0.025° = 800 发/秒`、`按转角发弹：1 秒 = 转速/单位角度 -> 800 发`。

## ③ 子弹停在「它涂到的地方」（用户：死了还往前冲一段）

原因是**额度不够涂完整条线**时，`PaintLine` 涂到中间就停了，但子弹的 `Pos`
还停在**线段末端** —— 于是子弹（和拖尾的头）落在它刚涂出来的领土**前面**。

修法：`PaintLine` 现在把「实际涂到线段的哪里」(0..1) 报出来，子弹据此把 `Pos`
和刚记下的那个拖尾点一起**收回去**。

自检：`额度涂不完时子弹停在**涂到的地方** -> 走了 0.163 m / 本来要走 1.60 m`。

# 第 75 轮：浮力跟不上新质量公式 + 弹力大砍 + 大球光效

## ① ★★ 「浮力托不起 262K 的球」——这是上一轮改密度**带出来的**

浮力区的力度是照「262K 那颗球的**重力**」标定的，但代码里**自己抄了一份质量公式**：

```csharp
// BuoyancyZone.HoldForce() 里
float mass = Mathf.Max(Cfg.BallMassMin, r * Cfg.BallMassPerRadius);   // ← 旧的「半径×系数」
```

而 `MultiplierBall` 上一轮改成了 `质量 = 密度 × 面积`。对 262K：

| | 质量 |
|---|---|
| 旧公式 | 0.443 |
| 新公式（密度 × 面积） | **2.415**（重了 5.45 倍） |

**浮力的力度没跟着涨，于是托不起来了。**

修法：把质量公式收成**唯一一处** `Cfg.MultiplierBallMass(value)`，
浮力和球都用它（就是这么一条规矩：同一个量只能有一个来源）。
自检也顺手把**自己抄的那份**删掉了（它抄的是旧公式，一改就假失败；真代码那边抄就真出 bug）。

- 球的 `Bouncy` 0.35 → **0.08**；
- 新增 `Physics2DConfig.ZoneWall`（**0.12**），增倍区里**所有**碰撞体换用它

- 战场那套 `Wall` 保持 1.0 —— 大球碰墙要**不损失能量地弹**，那是另一条规格（自检里也钉住了）。

# 设置面板：阵营数 / 阵营颜色 / 暂停继续

> 代码注释里把这轮记成「第 105 轮」。

三件事全部做成**运行时**的，而且整个面板由 `Cfg.EnableSettingsPanel` 一个开关决定存在与否
（关掉时 `Bootstrap` **连那个物体都不建**，HUD 一点不受影响）。

## ① 为什么换设置要「整棵树重搭」

阵营数一变，跟着变的东西太多：战场像素数组（`_owner` 按阵营数分配）、炮台 / 护盾 / 球、
领土花纹瓷砖、`Palette` 的三张表，以及 `Cfg` 里那些「按家数取不同值」的量
（护盾显示倍数、近防半径、初始领土半径……）。

与其给每个 `Build()` 都写一份「拆干净」的代码（漏一个就是幽灵炮台 / 漏一张 4 MB 贴图），
不如**只留一个根**：

| 物体 | 谁造的 | 重开时 |
|---|---|---|
| `[Game]` | `Bootstrap.BuildWorld()` | **整个 Destroy，下一帧重搭** |
| `[Settings]` | `Bootstrap.Boot()` | 留着（否则重开时自己就没了） |
| 场景里本来就有 | 用户 | 留着（`_preserved` 名单） |

顺序很重要：**先冻结（`timeScale = 0`）→ 拆 → 换阵营数 → 搭 → 恢复暂停态**。
阵营数如果在拆之前就写进 `GameSettings`，`Palette` 的缓存会立刻缩到新长度，
而旧 HUD 还在用旧下标画同一帧 → 越界。所以 `RebuildRoutine(int newFactionCount)`
是**拆完 `TearDown()` 之后**才落盘。

## ② 面板本身（`View/SettingsPanel.cs`）

IMGUI，不用 UGUI：整个工程的 HUD 就是 IMGUI 手画的，没有 Canvas / Prefab / 场景依赖。

- **阵营数**：2 / 4 / 8 / 16 四个按钮，点一下就是「应用 + 重开」；
- **暂停 / 继续**：按钮 + `空格`（`Cfg.PauseKey`）。暂停走 `Time.timeScale = 0`，
  IMGUI **不受 timeScale 影响**，所以面板照样能点；
- **阵营颜色**：每家一行 —— 色块预览 / 名字 / H S V 三根滑条 / 黑字白字 / 还原。
  H 范围 0–360°，S/V 上限 `Cfg.ColorSvMax = 1.6`
  （阵营表里有 S=1.1、V=1.5 的「溢出亮色」，不能夹到 1）；
- 面板上的改动先记在**工作副本**里，点「应用并重开」才落盘 ——
  否则拖一次滑条就 `PlayerPrefs.Save()` 一次；
- 16 家时列表可滚（安卓没有滚轮，所以滚动条**强制显示**，另加 ▲▼）；
- 界面按 `Screen.height / 900` 整体缩放（`GUI.matrix` 会连触摸坐标一起换算）。

## ③ 数据层（`Core/GameSettings.cs`）

静态类 + `PlayerPrefs`（键名 `mor.set.*`，不会和别的工程撞）：阵营数、每家 HSV 覆盖、
每家黑 / 白字覆盖。**没改过的项不写盘**（`HasHsv` / `_textBlack = -1` 表示用阵营表原值），
这样以后调阵营表还能自动生效。

★ 覆盖**按阵营数分开存**：`mor.set.hsv.h.<阵营数>.<下标>`，四套模式各占一个槽
（`GameSettings.SlotOf`）。四张阵营表本来就各自完整，4 家版调过的颜色**不许**串到 8 家版
（除了下标一样，那根本是另一批阵营）。上一版那种「按全局下标、不区分数制」的旧键，
`Load()` 会搬进**当前**这一槽再删掉，免得白丢一次调色。

★ 「还原」= **删掉覆盖**，不是写一条「和原值一样的覆盖」。后者会把阵营表钉死 ——
那家以后就不认 `FactionSetX.cs` 里的颜色了。
面板上的「恢复默认颜色」是**四套模式一起**清（真要全部回出厂），
只清当前这套没有独立入口。

`GameSettings.Version` 是**设置版本号**，任何一项改了 +1。`Palette` 的三个数组从
`static readonly` 改成**惰性重建的属性**，缓存键 = `(阵营数, Version)`：
调用方照旧按下标用，不用管缓存。

顺带改成属性的还有 `Cfg.ShieldVisualScale / ShieldMinRadius / CiwsRange / TurretNames`、
`TerritoryDeco.Styles` —— 原来 `static readonly` 会把第一次用到的表**永久**留在内存里。

## ④ 中文字形

## ⑤ 重开一局时的内存

`Destroy(GameObject)` **不会**带走运行时 `new` 出来的
`Texture2D / Mesh / Material / RenderTexture`。既然现在每换一次设置就重搭一次世界，
这几处必须自己收：

- `Battlefield`：1024² 贴图 + Sprite（一张 4 MB，漏一次就是 4 MB）；

**Play 模式下会拒绝执行** —— 那时换阵营数不会触发重建，
会留下「设置说 16 家、场上还是 4 家」的错位。

# 第 107 轮：浮力气泡改成「**每帧生成 x 个**」

> 用户：「浮力气泡的生成逻辑改一下，改成每帧生成 x 个而不是固定的数量」

## 原来是什么样

固定一池 **300 颗**（`Cfg.BuoyancyBubbleCount`）：开局沿通道撒满，之后**永远**是这 300 颗 ——
升到顶 / 活满 3 秒就**瞬移回底部**重新往上跑。通道里的数量是个常数，永远不会变。

## 现在是什么样

改成**流水线**：

| | 参数 | 说明 |
|---|---|---|
| 生成 | `Cfg.BuoyancyBubbleSpawnPerFrame = 3` | 每个**物理帧**（`FixedUpdate`，默认 50Hz）从底部生成 3 颗。**可以写小数**（2.5 = 有的帧 2 颗、有的帧 3 颗，攒够一颗才生成） |
| 消失 | `Cfg.BuoyancyBubbleLife = 3` | 升到顶 / 活满寿命就**真的消失**（不再瞬移回底部） |
| 上限 | `Cfg.BuoyancyBubbleMax = 400` | 同时存在的硬上限（也是对象池上限）。速率配太高时多出来的不生成，防止拖垮物理步 |

**稳态数量 ≈ 速率 ÷ `Time.fixedDeltaTime` × 一颗泡泡在通道里待的时间**
（3 颗/帧、通道 ≈ 2.1 秒走完 ⇒ 约 320 颗，和以前固定 300 颗差不多），
实际会上下浮动几颗 —— 那正是「一直在生成」的样子。

两个实现上的要点：

- **用物理帧而不是渲染帧**：不然 60Hz 和 144Hz 屏幕上密度会差一倍多。
- **池化**：泡泡建过就不销毁，消失时收回 `Stack` 复用（每秒生成上百颗，真 `Destroy` 的话
  GC 和物理重建都受不了）。每颗的半径在**出生时**重掷，所以复用的泡泡不会永远是同一个大小。
- **开局预热**：`Prewarm()` 先把通道铺到稳态数量（位置 / 年龄都随机），
  否则每局前 3 秒只有底部孤零零几颗，看着像坏了。预热只是初始化，之后的数量完全由「每帧生成 / 到顶消失」决定。

调参口诀：**稀了就加 `SpawnPerFrame`，卡了就减**（上限会兜住最坏情况）。
`SpawnPerFrame = 0` = 不再生成，通道会自己空掉（调试用）。

## 自检跟着改

- 删掉「泡泡数量 == 固定值」和「≥350 颗」那两条（固定数量已经不存在了）；
- 新增：`Cfg.BuoyancyBubbleCount` 这个字段**必须已经不存在**、硬上限容得下稳态数量；
- 新增：**跑一个物理步，累计生成数必须正好 +x**（用 `SpawnedCount` 而不是「当前活着几颗」——
  同一步里还会有到寿命消失的，净变化不等于生成数）；
- 新增：跑 400 个物理步后数量仍在 `(0, 上限]` 之间（不会无限涨、也不会跑空）；
- 出生点那条旧断言（「只有中间一条线」）和代码早就对不上了（实际是**三道源头**），
  改成直接反复问 `EmitLineOffset()`：只许返回 `0 / ±PegRowSpacing`，而且三道都要用到。

# 第 108 轮：泡泡**超界就回收**，不再反弹

> 用户：「把气泡改成超界就删除回收，不再反弹」

## 原来

`BuoyancyZone.FixedUpdate` 里，泡泡飘到通道左右边界时是这样处理的：

```csharp
// 旧代码：夹回边界 + 横向速度取反（掉头）
if (off > lim) { off = lim; if (vx > 0f) vx = -vx; }
else if (off < -lim) { off = -lim; if (vx < 0f) vx = -vx; }
```

于是泡泡会在两侧边缘**来回弹**，一直赖在通道里，直到升到顶或寿命到期。

## 现在

超过边界就直接 `Despawn(i)`（收回对象池），缺的由「每帧生成」补上：

```csharp
if (off > lim || off < -lim) { Despawn(i); continue; }
```

`lim = 通道半宽 − 最大泡泡半径`（≈ 2.78m），和以前夹的边界是同一个位置。
**判断必须放在「夹位置」之前**——先把 `off` 夹到 `lim` 就永远判不到超界了。

软推回（`BuoyancyBubbleLateralBand` / `BuoyancyBubblePushBack`）还在，用来把偏得远的泡泡
慢慢带回中心；但它不再负责「兜底」。顺带一提：现在 `LateralBand = 3.0` 被
`Clamp` 到 `lim`，所以实际上泡泡一到边界就被回收，软推回基本没机会生效——
想让它提前把泡泡拉回来，把 `LateralBand` 调小即可（比如 2.2）。

## 自检

新增：把一颗泡泡挪到通道外，跑一个物理步，**界外必须一颗不剩**
（不是被弹回来，而是真的被回收了）。

以前的问题：面板里点过「应用并重开」之后，`mor.set.hsv.*.4.0` 这条覆盖会**永远压着**
`FactionSet4.cs`，改表看不到效果（第 109 轮那个「配置不起作用」就是它）。

现在每条覆盖旁边多存一份**写入时的出厂值**：

| 键 | 内容 |
|---|---|
| `mor.set.base.h.<阵营数>.<下标>` | 写覆盖那一刻，阵营表里的 H |
| `mor.set.base.s.…` / `.v.…` | 同上，S / V |
| `mor.set.base.text.<阵营数>.<下标>` | 写覆盖那一刻的 `TextBlack` |

启动时 `GameSettings.Load()` 拿它和**现在**表里的值比：

- 一样 → 覆盖继续生效；
- 不一样 → 说明 `FactionSetX.cs` 被改过，**这条覆盖作废**（顺手把存档键删掉），直接用表里的新值；
- 没有这组键（第 110 轮之前的旧存档）→ 无法确认，同样作废。

这样一来「表 = 出厂配置」重新变成唯一真相：改表一定生效，面板调色只是**临时覆盖**，
直到你下次改表为止。

⚠️ 两个副作用要知道：

1. 升级到这一版后，**旧存档里的覆盖会被清一次**（包括 8/16 家版调过的）。4 家版的值已经
   同步进表了，所以看不出变化；8/16 家版如果调过，需要重新调一次。
2. 反过来也成立：你在面板里调好的颜色，只要之后又去改了表里那一家，覆盖就没了。
   想长期保留就把它同步进表（就像这次做的）。

`FactionSet.TableOf(int)` 因此改成了 public —— `Load()` 要按**每一档**的阵营数
去取出厂值比对，不能只看当前这一档。

只在**不同阵营**时额外判一次，两条门槛都是常量：

```csharp
// Cfg.VampireDrainThreshold = 0.5
// Cfg.VampireDrainFraction  = 0.5
if (IsVampire && other.Value < Value * 0.5)        // 敌方 < 自身 50%
{
    victim.Value -= victim.Value * 0.5;            // 吸走敌方 50%
    Value        += victim.Value * 0.5;            // 等量加给自己（自己不扣血）
}

    other.DrainEnemy(this);                        // 被动方向也生效
else
    正常大球：双方各扣 min(a,b) × 1/4;
```

# 第 112 轮：吸血球的两条修正

> 用户：「特效应该是每帧生成一个而不是只有一个，只有大球碰撞时有这个机制，子弹没有」

## ① 特效改成「每帧生成一颗独立的点」

旧实现预建 `ceil(fadetime / fixedDeltaTime) + 4` 个 `SpriteRenderer` 循环覆盖，每帧只改其中一个的位置和颜色：

- 帧率或淡出时间一变，就会把**还没淡完**的点提前盖掉；
- 角度是**乘法**增长（`_angle *= 1.02`），起始角抽到接近 0 时一整轮只转 0.09 rad，十几颗点几乎叠在同一个位置。

两条叠起来，画面上就是「只有一个点在转」。现在换成和浮力气泡（第 107 轮）同一套池模型：

| 项 | 现在 |
|---|---|
| 生成 | 每个**物理帧**按 `Cfg.VampireFxSpawnPerFrame = 1` 新生成一颗（支持小数累加） |
| 寿命 | 每颗点带自己的 `Age`，到 `VampireFxFadeTime = 0.2s` 才淡完回收 |
| 复用 | 淡完的点进 `_free` 栈，下次生成复用；**绝不覆盖还活着的点**；池按需扩容，上限 `VampireFxMaxPens = 64` |
| 起始角 | 下限 1 rad（`Random.Range(1, 2π)`），保证一轮至少转 ~100°，螺旋肉眼可见 |

螺旋本身（角度 ×1.02、半径 ×0.98、1.7s 一轮）一个字没动，只是把「一个循环池」换成「每帧 addpen」。`Attach` 不再预建任何点，第一帧才开始生成。

## ② 吸血只在大球碰撞时生效，子弹没有

核查结论：**子弹路径本来就没有吸血**（`Bullet` 早已去物理化，走 `BulletPool.ResolveBigBalls → Bullet.HitBigBall`，不经过 `BigBall.OnCollisionEnter2D`）。这一轮把这条不变式**显式钉死**，免得以后被顺手改坏：

- `BigBall.OnCollisionEnter2D` 的 `GetComponentInParent<BigBall>()` 守卫处写明这是「只有大球碰撞」的结构性保证；
- `BigBall.ResolveCrossFaction` 注释标为**吸血判定唯一入口**；
- `Bullet.HitBigBall` 开头写明刻意**不读** `big.IsVampire`：子弹打吸血球 = 打普通大球（己方并数值 / 引力球掷骰，敌方扣数值）；
- `SmokeTest` 加一条真断言：敌方子弹（数值 100）打 1M 吸血球 → 球只掉 100、子弹正常回收。

## 自检

- 特效：第一帧生成 1 颗、第二帧 2 颗同时可见（旧点不被覆盖）；跑满 32 帧后累计生成 32 颗、在场 < 32、对象数 < 32（证明淡完的点确实回收复用了）。
- 子弹：打吸血球只按普通大球扣数值，不触发 `DrainEnemy`。
- 本机改用 Windows 的 Unity 引用程序集全量编译 `Assets/Scripts` + `Assets/Editor`：**0 错误**。（`Tools/CompileCheck.csproj` 里写死的是 macOS 路径，在 Windows 上直接跑会报 519 个「找不到 UnityEngine 类型」，与代码无关。）

> 顺带：项目根目录新增 `RULES.md`，是**按当前代码**整理的现行规则速查。本文件是迭代日志，开头几节的数值多数已被后续轮次推翻 —— 查规则优先看 `RULES.md`，查「为什么这样」再看本文件。

# 第 114 轮：特效改成「一个圆 + 一条拖尾」

> 用户附参考图（亮色球面上一层细黑弧线，每条线一端一个浅色小圆点）：
> 「特效还是几乎看不出来，要的是一个圆形带一条拖尾算一个特效，每帧生成一个」

## 根因

第 112 轮虽然把「固定池循环覆盖」改成了「每帧生成」，但**每个特效仍然只有一个半径 0.01m 的小圆点** —— 14m 地图 / 1024px ≈ 73px/m，0.01m 半径只有 **1.5 像素直径**；深灰色又压在球外的黑背景上，等于没画。

## 改法

一个特效现在是一套 `Pen` 对象，含两个 `SpriteRenderer`：

| 部件 | 图形 | 尺寸 | 颜色 |
|---|---|---|---|
| 圆头 | `Primitives.Circle` | 半径 `0.05m`（直径约 7px），在 +X 端 | 白 `VampireFxHeadColor` |
| 拖尾 | `Primitives.Square` 拉成细长条 | 长 `0.5m`（约 36px）× 粗 `0.02m` | 深灰 `VampireFxColor` |

- 整套特效转到「+X = 运动方向」，拖尾从 x=0 往 −X 铺；运动方向取前后两帧位置差（新一轮第一颗退回解析切线），尾巴自然沿螺旋切线，连起来就是弧线。
- 长度 / 角度 / 圆头大小各带小幅随机（±25% / ±18° / ±20%），几十条尾巴才不会叠成一条粗带，而是像参考图那样散开。
- `VampireFxOrbitPad` 从 `+0.2` 改成 **`−0.05`**：整轮轨迹收在亮色球面**内**，深灰线才有对比；夹了 `2×PenRadius` 的底，数值很小的球也不会算出负半径。
- `VampireFxFadeTime` 从 `0.2` 提到 **`0.45s`**（同时在场约 27 套），球面才铺得开。
- 第 112 轮「每帧生成一套、各自淡出、淡完整套回池、绝不覆盖活着的」模型**完全保留**，池现在按整套 `Pen` 回收而不是单个 SpriteRenderer。

## 自检

- 新增 `VampireFx.TailCount`：断言在场的每个特效都带一条拖尾。
- 两帧后应有 2 套特效 = 4 个可见 SpriteRenderer（圆头 + 拖尾各 2）。
- 常量尺寸断言：圆头 ≥ 0.04m、拖尾 ≥ 0.3m，防止以后又被调回「看不见」。
- 全量编译 `Assets/Scripts` + `Assets/Editor`：**0 错误**。

# 第 115 轮：特效改成「球面随机散布的独立弧线」

> 用户贴了实机截图：浅蓝 99M 球上只有**两簇白色放射状刷子**，球面其它地方全空。

## 根因

第 114 轮虽然给每个特效加了「圆头 + 拖尾」，但**所有特效仍然排在同一条指数螺旋上**：

- 角度是**乘法**增长（`_angle *= 1.02^step`），每 1.7 秒重置一轮；
- 单个特效只活 `0.45s`，所以同一时刻只留下螺旋上短短一段弧（几十度）；
- 拖尾方向取「前后帧位置差」，跟着角度一起快速转（起始角大时每帧 4°+），27 帧跨 100°+；
- 于是这一小段弧上的白圆头连成一串、深灰细尾呈扇形散开 —— 就是截图里那两簇刷子。每轮重置一次，所以是两簇。

一句话：**「每帧生成一个」做到了，但生成点没有铺开**。参考图要的是整个球面均匀散布的细弧线。

## 改法

**去掉螺旋、去掉每轮重置**，每帧在球面上随机撒一个完全独立的特效：

| 项 | 现在 |
|---|---|
| 落点 | 随机极角 θ ∈ [0, 2π) + 随机半径 = 球半径 × [0.20, 0.85]，整条弧都在亮色球面内 |
| 朝向 | 该点局部切向（顺/逆时针随机）± `40°` 随机偏转，线大致沿同心弧又彼此交叉 |
| 拖尾 | **3 段短直线逐段转 12°**，拼成一条轻弯的弧；不再是直棒，也不再靠多帧连成弧 |
| 圆头 | 白色，半径 `0.04m`，在弧的前端 |
| 颜色 | 拖尾从 `0.2` 灰压到 **`0.06` 近黑**，粗 `0.02 → 0.025m`，免得被白圆头盖过去 |

删掉螺旋专用的 4 个常量（`VampireFxLife` / `AngleGainPerStep` / `DistanceGainPerStep` / `OrbitPad`），换成落点范围、段数、弯角、方向偏转 5 个。第 112 轮「每帧生成、各自淡出、淡完整套回池、绝不覆盖活着的」模型保留。

## 自检

- 新增 `VampireFx.LastSpawnPos` / `AngleForSmoke`（最近落点极角）；跑 20 帧断言极角跨度 > 180°，守住「铺满球面而不是挤成一簇」（全落在同一半圆的概率 ~4e-5）。
- 断言 `TailSegments > 1 && BendDeg > 0`（拖尾真的是弯的）。
- 每个特效部件数 = `1 圆头 + TailSegments 段`，两帧后应有 8 个可见 SpriteRenderer。
- 全量编译 `Assets/Scripts` + `Assets/Editor`：**0 错误**。

# 第 116 轮：把折线改成像样的拖尾

> 用户贴第 115 轮实机截图：「？这是拖尾？」—— 球面上散布的确实是一根根带尖角的**等粗折线**，不是拖尾。

## 三点不像拖尾

1. **等粗**：3 段宽度全是 0.025m，从头到尾一样粗，像画了条线而不是「拖」出来的。
2. **硬折角**：每段硬转 12°，3 段就有两个肉眼可见的尖角（截图里那些 "Z" / "7" 形）。
3. **方向太散**：切向 ±40° 偏转，同心感被冲掉，看着像随手涂鸦。

## 改法

| 项 | 第 115 轮 | 现在 |
|---|---|---|
| 段数 / 单段转角 | 3 段 × 12° | **6 段 × 6°**（总弯度相近，折角小到看不出来 = 平滑弧） |
| 宽度 | 等粗 0.025m | 从头 0.025m **线性收到尾尖 ×0.12**（`VampireFxTailTipWidthFrac`） |

# 第 117 轮：按 Algodoo poststep 原文重写

用户贴了原版代码，并强调「**这是放在 poststep 里的**」。前几轮全是看截图猜模型，现在有精确规格了。

## 原文在干什么

```text
tx = scene.addcircle({ radius := 0.01; colorhsva := [0,0,0.2,1];
                       _angle := rand.uniform01*2*pi; _distance := radius+0.2;
                       timetolive := 1.7;
        poststep := (e)=>{ pos = _bball.pos + [sin(_angle),cos(_angle)]*_distance;
                           _angle *= 1.02; _distance *= 0.98 } });
scene.addpen({ pos := tx.pos; size := tx.radius*2; fadetime := 0.2;
               zdepth := tx.zdepth+1; colorhsva := tx.colorhsva });
```

关键是**整段在 poststep 里**：每个物理步都执行一次 `addcircle` + `addpen`。所以：

- **每帧新建一套**，不是「一个点 + 固定池循环」（111/112 轮），也不是「预先画好的静态线段」（114~116 轮）。
- 这套里的小圆**自己会动**：每步 `pos = bball.pos + [sin(_angle), cos(_angle)] * _distance`，`_angle *= 1.02`、`_distance *= 0.98` → 沿自己的螺旋从球外收进球心。
- `addpen` 的 `pos := tx.pos` 绑在圆上跟着走，每步在圆的当前位置盖一个点，`fadetime := 0.2` 让旧点 0.2 秒淡出 ⇒ **尾巴是圆走过的轨迹**，渐隐、连贯、平滑，而且一直在动。
- 活 `timetolive := 1.7` 秒后整套消失；每套 `_angle` 独立随机 ⇒ 铺满球面。
- 圆和笔**同色** `[0,0,0.2,1]` 深灰，没有白圆头；笔图层比圆再高一层。

## 我之前错在哪

| 轮次 | 做成了什么 | 为什么不对 |
|---|---|---|
| 111/112 | 全局共用一个固定点池循环盖章 | 只有一个点在动 |
| 114 | 圆头 + 拖尾，但**所有特效共用一条螺旋**、粒子只活 0.45s | 只看得见螺旋上一小段 → 两簇白色刷子 |
| 115 | 删掉螺旋，改球面随机撒**静态**折线 | 没有运动轨迹，像涂鸦 |
| 116 | 给静态折线加渐细渐淡、更多段 | 折线再平滑也是画上去的线，用户：「？这是拖尾？」 |

根因一句话：**把「拖尾」当成预先画好的几何，没意识到它是一个运动物体留下的历史轨迹**；而且螺旋应该是**每套独立**的，不是全局共享。

## 实现

- `VampireFx.Pen` = 一个 `SpriteRenderer` 圆（addcircle）+ 一个 `TrailRenderer`（addpen），带自己独立的 `Angle` / `Distance` / `Age`。
- `FixedUpdate`：① 每套走一步 poststep（更新 `localPosition`，TrailRenderer 自动盖章）；② `age >= 1.7` 整套回池（`Clear()` + `emitting=false`，避免复用时连出旧线）；③ `SpawnDue()` 再新建一套。
- `TrailRenderer.time = 0.2`（fadetime）、`startWidth = endWidth = size`（addpen 等粗圆点）、`colorGradient` 让 alpha 沿时间从 1 掉到 0；材质 / 渐变全局共享一份，避免上百次 SetPass。
- 颜色统一深灰，没有白圆头；`_pdsz <= 0` 时整套立刻收掉。

**尺度换算**（原文数值相对 Algodoo 球半径约 1）：`radius := 0.01` → `VampireFxPenRadiusFrac = 0.025`（99M 球约 0.04m ≈ 6px 直径）；`_distance := radius + 0.2` → `VampireFxOrbitStartFrac = 1.2`；`×1.02` / `×0.98` 按 `VampireFxAlgodooFps = 30` 换算成与帧率无关。上限 160 套（1.7s × 60fps ≈ 102），材质共享但仍有约 200 个 Renderer，场上吸血球很多时可下调 `VampireFxSpawnPerFrame`。

## 自检

- 常量断言守住原文：每帧 1 套、`timetolive 1.7`、`fadetime 0.2`、`×1.02`、`×0.98`。
- `TrailCount == LivePenCount`（每套都带笔）、`ActiveDistance` 逐帧变小（圆真的在走螺旋）、2 套 = 2 圆 + 2 笔、每套起始角随机跨度 > 180°、跑够 1.7s 后整套回收复用。
- 全量编译 `Assets/Scripts` + `Assets/Editor`：**0 错误**。

# 第 118 轮：拖尾调细 + 修「走到某些位置就消失」

> 用户：「拖尾再细一点，有个奇怪的问题是到了一些位置特效会直接消失」

## 消失的根因

不是图层压住（场上最高 `sortingOrder` 就是笔迹的 63，没有别的东西盖在它上面），而是 **TrailRenderer 的采样阈值**：

- Algodoo 的 `addpen` **每步都盖章**，不看位移；
- Unity 的 `TrailRenderer.minVertexDistance` 要物体移动超过阈值才补顶点。第 117 轮给了 `0.004m`，螺旋上位移小的区段（起始角小、或 `_distance` 已收缩）一步走不到 0.004m → **一个点都不盖，拖尾凭空断掉**。
- 雪上加霜：`_angle := rand.uniform01 * 2π` 可能抽到接近 0，而角度是**乘法**增长（`_angle *= 1.02`），起始 0.01 rad 时整套 1.7 秒只转 0.02 rad，几乎不动、笔迹全堆在一个点上 —— 看着也是「消失」。

## 改法

| 项 | 之前 | 现在 |
|---|---|---|
| `VampireFxTrailMinVertex` | `0.004` | **`0`**（每帧必采样 = addpen 语义；每套约 12 个顶点，开销可忽略） |
| 起始角 | `[0, 2π)` | **`[0.35, 2π)`**，只避开退化，正常随机分布不变 |
| 笔迹宽度 | `size = 圆直径` 等宽 | **圆直径 × `0.35`**（99M 球约 2px），圆头仍保持约 6px 看得见 |

`SmokeTest` 加三条断言分别守住这三个值。

## 另外两个「看着像消失」但属正常

- 粒子从 `_distance := radius + 0.2`（球外 20%）起转，深灰 `[0,0,0.2,1]` 在战场近黑背景上对比很低 —— 刚生成那一小段不容易看见。想让整套从头可见，把 `VampireFxOrbitStartFrac` 从 `1.2` 调到 `1.0` 左右。
- 球中央的 "99M" 是 **IMGUI**，永远画在最上层，粒子飘到字后面会被遮住；这不是 `sortingOrder` 能解决的。如果消失的位置正好在文字上，就是它。


问题就在这一行：**碰撞造成的纵向速度变化被整帧丢弃**。大球压住泡泡时，物理引擎算出
`velocity.y` 变慢甚至变负，但下一帧 `FixedUpdate` 又把它覆盖回 `Vy`（那个只加不减的累加器），
所以泡泡看起来「被压住了速度也不受影响」，或者被压下去之后突然跳回原来的速度。

## 改法

删掉 `Bubble.Vy`，改成**读刚体当前速度再加加速度**：

```csharp
Vector2 v = b.Rb.velocity;                 // = 上一步物理 + 碰撞之后的结果
float vy = v.y + Cfg.BuoyancyBubbleRiseAccel * dt;
b.Rb.velocity = new Vector2(vx, vy);
```

这样「被挡住 → 速度掉下来 → 分开后从那个速度继续加速」是自然结果，不需要额外状态。

## 连带：阻尼开始真正生效

以前 `Rigidbody2D.drag = 0.4` 在纵向被那个覆盖写法绕过了（每帧重置），现在读刚体速度，
阻尼也就正常作用：

- 纵向收敛到 `RiseAccel / Drag = 3 / 0.4 ≈ 7.5 m/s`（原来一路加到 9.4 m/s）；
- 通道内到顶 **≈2.3s**（原来 1.79s），稳态数量 ≈**343 颗**（原来 ≈268，上限 400 仍够）。

把 `drag` 提成常量 `Cfg.BuoyancyBubbleDrag = 0.4f`（原来是 `NewBubble` 里的魔法数），
想恢复原来那种「一路加速」的手感就调到 `0.2`（≈2.0s 到顶）或 `0`（≈1.79s，完全不阻尼）。

- `SmokeTest` 新增：取一颗刚生成的泡泡，把纵向速度设成 `−2`（模拟被压下来），
  跑一个物理步后必须是 `−2 + RiseAccel × dt`，**不能跳回出生速度**。
- 全量编译 `Assets/Scripts` + `Assets/Editor`：**0 错误**。

# 第 127 轮：气泡推力加大（加速度 3 → 30，阻尼同步 0.4 → 4）

> 用户：「改完之后没推力了，推力大一点」

## 为什么上一轮之后「没推力」了

第 126 轮把「每帧强行写回速度」改成「从刚体当前速度继续累加」之后，物理上是对的，
但**推力**也跟着变了：

| | 第 126 轮之前 | 第 126 轮之后 |
|---|---|---|
| 被大球压住时 | 每帧把速度写回 4~9 m/s ⇒ 等效冲量 `m × v / dt ≈ 11 N` | 速度被碰撞压到 ≈0，每步只 +`a·dt` ⇒ 推力 `m × a = 0.025 × 3 = 0.075 N` |
| 结果 | 顶得很猛 | 推不动（最轻的球重 `0.1 × 9.81 × 0.5 = 0.49 N`） |

所以「有劲」其实是那个被删掉的假冲量。正确做法是让**加速度**承担推力：

```
顶球推力 = 质量 × 加速度        （压住时唯一的作用量）
自由终端速度 = 加速度 ÷ 阻尼     （不封顶时）
```

两个式子共用 `加速度` 一个量，所以**加速度和阻尼必须一起调**，才能只改推力、不改上升速度。

## 改法

| 常量 | 之前 | 现在 | 结果 |
|---|---|---|---|
| `BuoyancyBubbleRiseAccel` | `3` | **`30`** | 单颗顶球推力 `0.025 × 30 = 0.75 N`（≈最轻球重量的 1.5 倍，几颗一起顶就抬得起来） |
| `BuoyancyBubbleDrag` | `0.4` | **`4.0`** | 终端速度仍是 `30 / 4 = 7.5 m/s`（和之前完全一致） |
| 通道内到顶 | ≈2.3s | **≈1.71s** | 稳态数量 ≈256 颗（上限 400 仍够） |

原文那个 `0.1/步`（= 3 m/s²）保留成 `BuoyancyBubbleFreeRiseAccel`，只作参考 ——
它是「自由上浮」的观感值，但顶不住球。

## `TransitTime` 也跟着改了

以前按「匀加速 + 封顶」算，现在必须算**带阻尼**的解（`dv/dt = a − k·v`）：

```
s(t) = V·t + (v0 − V)(1 − e^{−k·t}) / k ，V = a / k
```

用二分求根（只在预热 / 自检时算一次）。否则稳态数量会被算成 137 颗，开局预热会明显偏稀。

- `SmokeTest`：新增「单颗推力 `m×a ≥ 0.9 × 最轻球重量`」「终端速度 = `a/drag` 落在 3~20 m/s」两条；
  原文换算值改由 `BuoyancyBubbleFreeRiseAccel` 校验。
- 全量编译 `Assets/Scripts` + `Assets/Editor`：**0 错误**。

# 第 129 轮：去掉气泡阻尼，改回「加速度 + 速度上限」

> 用户：「不要阻尼，改回之前的」

## 为什么又要把上限打开

阻尼去掉之后，速度会一路累加：`4 + 30t`，走到通道顶时已经 **27 m/s**，
一物理步走 0.54m —— 比泡泡直径（0.2~0.44m）还大，会**直接穿过大球**，推力和碰撞全失效。
所以改回第 126 轮之前那套写法：**加速度负责推力，速度上限负责封顶**。

- 0.13s 内从 4 加到 8 m/s，之后匀速 8 m/s；
- 通道内到顶 **≈1.53s**，稳态 **≈229 颗**（上限 400 够）；
- 顶球推力 `0.025 × 30 = 0.75 N/颗` 不变。

## 一个连带变化

`drag = 0` 之后，横向速度也不再有物理衰减（原来 `drag = 8` 把它磨得很厉害），
泡泡会更明显地左右飘 —— 只靠 `BuoyancyBubbleLateralBand`（±3.3m）那条硬阈值关着。

- `SmokeTest`：`RiseSpeedMax <= 0` 那条改成「**必须**有上限兜底（> 出生速度）」，
  另加一条 `Drag <= 0`；终端速度的算法改成「有阻尼取 `a/drag`，否则取上限」。
- 全量编译 `Assets/Scripts` + `Assets/Editor`：**0 错误**。
